# Simpul P16 — Backend SQLite Terenkripsi SQLCipher (SEC) + BM-07 Real-SQLite

Tanggal: 2026-11-14 · Branch: `vibe/simpul-p16-2a5227` · Basis: main (merge PR #22)

## Ringkasan

Item PRD terakhir yang selama ini diblokir ketersediaan pustaka:

1. **BM-07** — benchmark kini berjalan di atas backend **SQLite nyata**
   (bukan fallback JSON) bila libsqlite3 tersedia.
2. **Backend SQLite terenkripsi** — `index.db` kini ikut dienkripsi pada
   `lock` dan didekripsi pada `unlock` via **SQLCipher** (`sqlcipher_export`),
   memakai kunci vault yang sama dari hierarki SEC-07.

## Yang dibangun di sandbox (environment, bukan repo)

Sandbox Debian 13 tanpa akses root (sudo diblokir `no_new_privs`) dan `curl`
diblokir proxy — semua pustaka dikompilasi dari sumber via `git clone` ke
`$HOME/.local`:

- **OpenSSL 3.3.2** (statis, `-fPIC`) → header + `libcrypto.a` untuk SQLCipher.
- **tcl 8.6** → `tclsh8.6` yang dibutuhkan generator amalgamation SQLite.
- **SQLCipher v4.6.1** → amalgamation `sqlite3.c` terintegrasi codec, lalu
  dikompilasi sendiri menjadi `$HOME/.local/lib/libsqlcipher.so`
  (`-DSQLITE_HAS_CODEC -DSQLCIPHER_CRYPTO_OPENSSL -DSQLITE_ENABLE_FTS5`).

Tidak ada binari atau path sandbox yang di-commit ke repo; di mesin pengguna
cukup `libsqlcipher` dari paket distro (atau tanpa itu, semua fitur tetap
berjalan dengan degradasi yang sama seperti sebelumnya).

## Perubahan kode

### `vault_index_sqlite.dart` (dan stub-nya)

- **Loader cerdas** (`open.overrideFor` untuk Linux): mencoba
  `SIMPUL_SQLCIPHER_PATH` (env), `$HOME/.local/lib/libsqlcipher.so`,
  `libsqlcipher.so`, `libsqlite3.so`, lalu `libsqlite3.so.0` — memperbaiki
  kasus umum Debian/Ubuntu yang hanya mengirim runtime `.so.0` tanpa symlink
  dev (penyebab semua test sqlite skip sebelumnya).
- **`sqlcipherAvailable`** — deteksi via `PRAGMA cipher_version` pada db
  in-memory, hasil di-cache.
- **`tryOpen(dbPath, {vaultKey})`** — dengan `vaultKey` membuka db
  SQLCipher: `PRAGMA key = "x'<hex kunci vault>'"` lalu verifikasi baca
  `sqlite_master` (kunci salah → `VaultCryptoException`, fail-closed — tidak
  ditelan sebagai "pustaka tidak tersedia").
- **`isFileEncrypted(path)`** — db SQLCipher diawali salt acak, bukan magic
  `SQLite format 3\0`.
- **`encryptFileInPlace` / `decryptFileInPlace`** — migrasi bolak-balik via
  `ATTACH ... KEY` + `sqlcipher_export` + `DETACH`, atomic tmp+rename.

### `vault_modes.dart`

- `lock`: `index.db` yang ada kini **dienkripsi** (bukan ditolak) bila
  SQLCipher tersedia; tanpa SQLCipher tetap ditolak dengan pesan jelas
  (perilaku lama).
- `unlock`: `index.db` terenkripsi didekripsi balik dengan kunci vault
  (password atau share Shamir — keduanya bekerja).
- `status`: memuat status `index.db` di peta `files`.

### CLI & bridge

- `_openIndexFile` (CLI) dan `_openIndex` (bridge): backend sqlite kini
  menerima `vaultKey` dari kripto vault — perintah `search`, `sync`, `ask`,
  dll. bekerja pada vault terkunci berbackend sqlite dengan
  `SIMPUL_PASSWORD`, sama seperti backend JSON.
- `simpul bench [--backend auto|json]` — `auto` (default) memakai sqlite
  nyata (BM-07); `json` memaksa fallback untuk perbandingan.

## Keputusan desain

- **Kunci vault mentah (raw hex) untuk `PRAGMA key`**, bukan passphrase:
  terikat pada hierarki SEC-07 yang sudah ada (password→KEK→vault key),
  sehingga unlock via Shamir recovery share otomatis membuka sqlite juga;
  KDF SQLCipher internal (PBKDF2-SHA512) hanya jadi lapisan kedua.
- **`sqlcipher_export` untuk migrasi** — jalur resmi SQLCipher, mempertahankan
  schema termasuk tabel virtual FTS5.
- **Kunci salah = exception, bukan fallback** — melanggar kontrak lama
  `tryOpen → null` secara sadar untuk kasus terenkripsi agar tidak ada jalur
  fail-open.
